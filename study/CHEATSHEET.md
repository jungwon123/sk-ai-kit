# CHEATSHEET — 사람용 요약 (Codex는 읽지 않는다)

시험 중 Codex가 일하는 동안, 담당자에게 묻기 직전, 결과를 해석할 때 펼쳐 보는 한 장. 루트로 복사하지 않는다.
반도체 개념을 자세히 보려면 `kit/study/SEMICONDUCTOR.md`(공정·메모리·테스트·결함·수율 모델·손 계산), 분석 방법은 `kit/domain/semiconductor-methods.md`.

## 1. 반도체 핵심 개념

- **단위**: lot(웨이퍼 약 25장) → wafer(칩 수백~수천) → die(칩) → bin(테스트 결과 코드)
- **EDS**: 웨이퍼 상태에서 칩마다 전기 테스트 → bin → 좌표에 그리면 웨이퍼 맵
- **리페어**: 메모리는 여분 셀로 불량을 고침 → 리페어 전·후 수율이 다르다. 공정 결함은 보통 리페어 전
- **수율은 곱**: 라인 × 다이 × 최종 테스트. "수율"이 어느 층인지 먼저 맞춘다
- **결함은 몰린다**: 같은 웨이퍼·lot의 칩은 독립이 아니다 → 칩 단위 검정은 p값 과장
- **수율 모델**: 포아송 Y = e^(−A·D₀), 음이항 Y = (1 + A·D₀/α)^(−α). 칩 면적이 다르면 결함 밀도 D₀로 비교
- **적층(HBM)**: 스택 수율 ≈ 다이 수율^단수 × 접합 수율. 0.98¹² ≈ 78%
- **샷 반복 불량** → 레티클 의심. **큐타임** 초과 → 불량 가능. **가장자리 칩**은 원래 불량률이 높다

## 2. 통계 판단 (가장 중요)

| 상황 | 할 것 | 하지 말 것 |
| --- | --- | --- |
| 두 설계·조건 불량률 비교 | 웨이퍼(lot) 단위로 집계해 차이 + 95% CI | 칩 수십만 개로 z검정 후 "p<0.001" |
| 전체와 층별 결론이 다름 | 장비·기간·제품·위치별로 나눠 보고, 교란 의심 (심슨의 역설) | 전체 숫자만 보고 |
| "나빠지지 않았나"가 기준 | 비열등성: 차이 CI 상한이 허용 한계 δ보다 작은지 | "유의하지 않음 = 차이 없음" |
| 장비 수십~수백 대 검정 | FDR(BH) 보정, 시간 순서·메커니즘으로 교차 확인 | 유의한 것만 골라 보고 |
| 표본이 적음 | "검출 가능한 최소 차이는 X%p"로 말하기 | 결론 단정 |
| 공정 안정성 | 관리도 + 규칙(3σ 밖 1점, 같은 쪽 연속 8점 등), Cpk ≥ 1.33 | 안정 안 된 공정에 Cpk |
| 예측 모델 | lot 단위 GroupKFold, 시간순 분할, 불균형이면 재현율·정밀도 | 칩 무작위 분할, 정확도 98% |

## 3. 현업 앞에서 쓰는 문장

- "웨이퍼 단위로 보면 신설계 평균 수율은 기존 대비 −1.2%p입니다(95% CI −2.0 ~ −0.4, 웨이퍼 24 대 26장)."
- "칩 단위로 검정하면 p값이 과장되어서 웨이퍼를 분석 단위로 잡았습니다."
- "칩 면적이 달라 면적당 결함 밀도로 환산해 비교했습니다."
- "전체로는 차이가 있지만 장비별로 나누면 사라집니다. 생산 배분 차이로 보입니다."
- "장비 120대를 검정해 FDR로 보정했고, 보정 후 남는 것은 C 장비 2번 챔버뿐입니다."
- "유의하지 않다는 것이 차이가 없다는 뜻은 아닙니다. 현재 표본으로 검출 가능한 최소 차이는 약 X%p입니다."
- "상관 근거입니다. split-lot으로 확인하시길 제안드립니다."
- 피할 말: "AI가 원인을 찾았습니다", "p<0.001이니 확실합니다", 불균형 데이터의 "정확도 98%"

## 4. 담당자에게 물을 것 (D1-S 요약, 숫자를 보여 주며 3~5개씩)

1. 수율 기준은 리페어 전·후 중 무엇이고, 어느 bin을 불량으로 세나요? (bin별 건수 제시)
2. 엔지니어링·hold·rework lot은 빼도 되나요? (각 개수 제시)
3. 두 설계안은 같은 라인·장비·기간에 생산됐나요? 칩 면적은 같나요?
4. 시각 기준은 테스트 시각인가요, 공정 진행 시각인가요?
5. 의미 있는 차이는 몇 %p이고, 채택 기준은 "개선"인가요 "나빠지지 않음"인가요?
6. 그 기간에 PM·레시피·자재 변경이 있었나요?

답을 받으면 바로 T1에 붙여 넣는다(시각 포함 기록). 판단(분석 단위, 검정 방법)은 묻지 말고 내 안으로 확인받는다.

## 5. 백엔드 설명 요점

- **서빙**: uvicorn 프로세스 하나가 API와 화면을 서빙, `0.0.0.0:포트`. 시작할 때 lifespan에서 데이터 적재·DB 초기화
- **진실의 원천**: SQLite. 메모리 캐시는 재시작하면 다시 만든다. 잃는 것은 진행 중이던 요청뿐
- **계산 위치**: 무거운 계산은 실행 시 한 번 → 결과 테이블, 조회 API는 읽기만
- **재실행 안전**: UNIQUE + UPSERT, 실패하면 트랜잭션 롤백
- **`def` vs `async def`**: pandas·sqlite3는 블로킹 → `def`(스레드풀)
- **상태코드**: 422 입력 오류, 404 없음, 409 충돌, 500은 내부 정보 숨기고 로그
- **배포 전제**: 공정 데이터는 기밀 → 사내망 배포, 외부 API 없음, 의존성 버전 고정(사내 미러·Docker), 운영 시 사내 계정 연동과 조회·내보내기 감사 로그
- **10배**: 인덱스·캐시·페이지네이션 / **100배**: chunk·Postgres·작업 큐. 처음 깨지는 곳을 말한다

## 6. AI가 짠 코드 볼 때 (승인 직전 30초)

- [ ] 합의한 기준값·경계(이상/초과)가 테스트에 들어 있나
- [ ] 예외를 삼키는 `except: pass`, 하드코딩 값, 테스트만 통과시키는 꼼수는 없나
- [ ] 분석 단위가 칩이 아니라 웨이퍼·lot인가, 시드 고정됐나
- [ ] 정제 전후 건수와 제외 사유가 남나
- [ ] 바꾸는 파일이 범위 안인가

## 7. 서술형 5분 답안 틀

**사실(파일·함수·숫자) → 이유와 버린 대안 → 약점 → 검증.** 5~8문장.
1. 한 줄 목적: "___ 데이터를 받아 ___를 계산해 ___가 ___를 결정하게 했다."
2. 흐름: CSV → 검증(규칙 N개) → 저장(키, UPSERT) → 계산(위치와 이유) → API → 화면
3. 트레이드오프: "A 대신 B, 이유 ___, 대가 ___"
4. 예외: 대표 2개와 처리 방식, 처리 못 한 것 1개
5. 검증: 테스트 N개, 손 계산, 시뮬레이션, 담당자 확인 시각
6. 확장: 처음 깨지는 곳과 대안
